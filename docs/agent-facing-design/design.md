# agent-facing-design 设计文档

## 设计目标

目标：

1. **建立 Agent-facing 验收标准**：把“人能读懂”升级为“冷启动 Agent 能仅凭文档独立完成任务”。
2. **约束 CLI 和文档的可执行性**：要求 CLI `--help`、输出格式、错误信息、路径回显和文档示例都能被 Agent 直接使用。
3. **降低 Agent 工具发现成本**：当多个脚本或数据源服务同一任务链路时，推动统一入口和统一输出视图。
4. **提供可验证闭环**：通过隔离 subagent 冒烟验收，发现文档缺参、缺路径、缺前置条件或语义歧义。

非目标：

- 不做纯人类阅读体验优化。
- 不替代具体业务工具的实现。
- 不替代项目进度保存或会话恢复。
- 不要求所有输出强制 JSON；格式应由数据形状决定。

## 方案概览

流程简述：

```text
被测工具 / 文档 / CLI
        |
        v
识别 Agent 消费场景
        |
        +--> CLI 契约审查
        +--> Agent 文档审查
        +--> 统一视图模型审查
        +--> 多脚本合并判断
        |
        v
生成整改建议或直接修改
        |
        v
隔离 subagent 冒烟验收
        |
        v
输出验收结果与剩余风险
```

关键模块：

- **CLI 自描述性**：`--help` 必须独立说明子命令、输入、输出、默认值、互斥参数、前置条件和产出路径。
- **Agent 适配输出**：默认输出应模型可读，stdout / stderr 分离，退出码表达成败，错误信息可操作。
- **统一视图模型**：多数据源先收敛成最小充分模型，避免 Agent 反复回查原始源。
- **Agent-facing 文档**：文档必须提供可复制命令、输出说明、参数默认值、失败处理和前置条件。
- **Subagent 冒烟验收**：用隔离上下文模拟真实冷启动 Agent，测试文档是否自足。
- **文档腐化审计**：检查路径、命令、参数、session ID、URL、端口和临时 workaround 是否过期。

依赖与约束：

- 需要能读取被测文档或工具说明。
- 如果要实测 CLI，需要本地能运行对应命令。
- 如果做 subagent 冒烟验收，必须避免向 subagent 泄露当前会话推理、预期答案或补充说明。
- 输出应区分“已实测”“从文档推断”“尚未验证”。

## 关键取舍

### 1. 默认模型可读，而不是默认人类漂亮

- 方案 A：默认输出彩色表格，人类体验更好。
- 方案 B：默认输出模型可读，漂亮输出通过 `--human` 或 `--pretty` 显式开启。
- 决策结论：选择方案 B。
- 原因：Agent 是主要消费者时，默认输出必须无歧义、易解析；彩色表格和对齐文本会提高解析成本。

### 2. `--help` 是合同，不是索引

- 方案 A：`--help` 只列入口，详细语义放外部文档。
- 方案 B：`--help` 直接写清输入、输出、默认值、互斥关系和前置条件。
- 决策结论：选择方案 B。
- 原因：Agent 可能只能拿到 `--help`，也可能无法可靠追外部链接。`--help` 不完整会导致任务执行断点。

### 3. Subagent 验收必须隔离

- 方案 A：让当前 Agent “假装冷启动”审查文档。
- 方案 B：使用隔离 subagent，只给原始文档和业务目标。
- 决策结论：选择方案 B。
- 原因：当前 Agent 已经知道上下文和预期修复方向，会掩盖文档缺陷。隔离实验能减少假阳性。

### 4. 统一视图模型不能过度收敛

- 方案 A：尽可能删除数据源差异，输出极简模型。
- 方案 B：删除私有实现细节，但保留消费者完成任务所需的语义字段。
- 决策结论：选择方案 B。
- 原因：砍掉必要字段会迫使 Agent 回查原始数据源，抵消统一视图的收益。

### 5. 检查清单放 skill 内的 references/，不放 docs/

- 方案 A：SKILL.md 保持单文件，所有清单内联（原状，237 行）。
- 方案 B：清单下沉到 `docs/agent-facing-design/`（如 runbook.md），SKILL.md 引用。
- 方案 C：清单下沉到 `skills/agent-facing-design/references/`，SKILL.md 按对象类型路由引用。
- 决策结论：选择方案 C。
- 原因：方案 A 使 SKILL.md 成为原则手册而非执行合约，且每次触发全量加载；方案 B 在分发时断链——skills CLI 只安装 `skills/<name>/` 目录，消费端拿不到 `docs/`；方案 C 让清单随 skill 分发，SKILL.md 只保留路由和步骤，按需加载。
- 连带约束：`docs/agent-facing-design/runbook.md` 不再复制清单内容，只保留操作顺序和输出模板，以 references/ 为唯一权威来源。

### 6. 冒烟验收的工具禁令用 prompt 约束兜底

- 方案 A：等平台支持逐调用工具白名单后再落地冒烟验收。
- 方案 B：文档全文内联进 prompt（消除 Read 依赖）+ prompt 显式禁止工具 + 结果有效性自查（发现使用工具迹象即作废重跑）。
- 决策结论：选择方案 B。
- 原因：Claude Code 的 Agent 工具当前无法逐调用裁剪 subagent 工具集；方案 B 用三层软约束把泄漏风险压到可接受，且立即可执行。已知残余风险：subagent 违令用工具且未在回复中留下痕迹时无法检出。

## 数据与接口

输入：

- 被测 CLI 的命令入口和 `--help` 输出。
- 被测文档原文，如 `AGENTS.md`、`SKILL.md`、runbook 或 README。
- 目标 Agent 的能力边界，如是否可运行命令、是否可读代码、是否有网络或生产权限。
- 3-5 个真实任务场景。

输出：

- Agent-facing 可用性审查结论。
- 需要修改的 CLI、文档或输出模型建议。
- Subagent 冒烟验收结果。
- 剩余风险和未覆盖场景。

中间状态：

- CLI 检查清单。
- 文档自足性检查清单。
- 统一视图模型草案。
- Subagent prompt 和场景列表。

兼容性说明：

- 对人类友好的输出不被禁止，但必须是显式 opt-in。
- 现有 CLI 若无法立即调整默认输出，应至少提供稳定的机器可读模式，并在文档中明确命令。
- 破坏性操作必须保留人工或显式 flag 门槛，不能为了 Agent 自动化而弱化安全边界。

## 风险与缓解

| 风险 | 触发条件 | 影响 | 缓解措施 |
| --- | --- | --- | --- |
| 过度偏向 Agent 导致人类体验下降 | 只提供机器可读输出 | 人类调试成本升高 | 提供 `--human` / `--pretty` 作为显式模式 |
| subagent 验收泄露信息 | prompt 暗示子命令或预期答案 | 文档缺陷被掩盖 | 只提供原始文档和业务目标，不提供补充解释 |
| 统一视图砍掉必要字段 | 只追求紧凑输出 | Agent 被迫回查原始数据 | 用“仅凭输出能否完成任务”判断字段保留 |
| CLI help 腐化 | 参数更新后文档未同步 | Agent 执行错误命令 | 审计时交叉比对 `--help` 与文档 |
| 破坏性操作误执行 | Agent 重复运行删除或覆盖命令 | 数据丢失 | 要求 `--dry-run`、显式 flag 和清晰影响预览 |
| 错误信息不可操作 | 只输出泛化异常 | Agent 无法恢复 | 错误中给出缺失参数、可选值和示例命令 |
