# progress-manager 设计文档

## 设计目标

- 统一保存、更新和恢复项目进度的入口。
- 以任务级项目根目录为稳定锚点，避免命令执行目录变化后读写不同的 `.work-progress/`。
- 用 Markdown 文件保存可恢复的代码认知、执行计划和下一步动作，不引入数据库。
- 非目标：自动合并不同 Git 工作树的进度、递归搜索所有子目录中的历史进度或维护额外状态数据库。

## 方案概览

- 架构：`SKILL.md` 负责动作路由、共享根目录解析和质量约束；`save-progress.md` 与 `resume-progress.md` 分别承载保存和恢复细则。
- 存储：未完成任务位于 `<进度根目录>/.work-progress/*.md`；完成任务位于 `<进度根目录>/.work-progress/archive/*.md`。
- 根目录解析：用户显式路径 > 宿主项目/工作区根目录 > Git 工作树根目录 > 当前目录降级。
- 约束：每次 save 或 resume 只解析一次根目录；首次操作前先显式告知用户 `.work-progress/` 绝对路径，后续始终使用该路径。

## 关键取舍

### 进度目录的锚点

- 方案 A：使用每条命令的当前目录。
  - 优点：无需解析。
  - 缺点：在 workspace、仓库根目录和子包之间切换时会产生多个进度目录。
- 方案 B：只使用 Git（分布式版本控制系统）仓库根目录。
  - 优点：仓库内路径稳定。
  - 缺点：无法覆盖非 Git 项目和宿主明确分配的上层 workspace。
- 方案 C：按显式路径、宿主根目录、Git 根目录和当前目录的优先级解析。
  - 优点：既尊重用户和宿主的任务边界，又兼容通用 Git 与非 Git 环境。
  - 缺点：多工作区时需要做唯一性判断。
- 决策：采用方案 C。多个根目录都匹配时要列出候选，不得同时读写多处。

### 状态存储

- 方案 A：在文件名中维护 `doing|blocked|done`，状态变化时重命名。
- 方案 B：以 `.work-progress/` 与 `archive/` 的目录位置表示未完成与完成，暂停、卡住和风险写入文件内容。
- 决策：采用方案 B，避免状态变化导致文件链接和标识频繁改变。

## 数据与接口

- 输入：用户的 save/resume 意图，可选的根目录、`.work-progress/` 目录、进度文件路径或任务关键词，宿主提供的项目/工作区根目录。
- 处理：项目根目录直接使用；`.work-progress/` 目录取父目录；进度文件向上定位 `.work-progress/` 后取其父目录。将选定根目录规范化为绝对路径；必要时运行 `git -C "<起点目录>" rev-parse --show-toplevel`，其输出应为当前 Git 工作树根目录的绝对路径。
- 中间状态：本次操作锁定的进度根目录和进度文件绝对路径；不额外落盘。
- 输出：操作前的 `.work-progress/` 目录绝对路径提示；新建、更新、归档或读取的 Markdown 文件；以及包含该文件绝对路径的操作后摘要。
- 兼容性：不自动迁移旧的分散 `.work-progress/`；用户显式给出旧路径时仍可读写。

## 风险与缓解

1. 多个宿主工作区同时匹配。
   - 触发：任务涉及的文件跨多个工作区，或无法从上下文判定所属项目。
   - 影响：可能读写错误项目的进度文件。
   - 缓解：列出候选绝对路径并请用户选择；禁止同时写入多个目录。
2. 显式路径失效或缺少当前操作所需权限（save 需读写，resume 需读取）。
   - 影响：自动降级会把进度写到非预期位置。
   - 缓解：报告绝对路径并停止，不做隐式降级。
3. 任务在两个独立 Git 工作树之间迁移。
   - 影响：两个工作树根目录的 `.work-progress/` 天然隔离。
   - 缓解：迁移后显式传入原进度文件或根目录路径；不自动跨工作树搜索。
